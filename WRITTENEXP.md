# Part 1
I created three tables before merging: two from the 2017 hormone paper (BAP x IBA and BAP x NAA) and one from the 2016 macronutrient paper (the highlighted subset of ion-concentration combinations). Although only the BAP x IBA table was highlighted in the hormone paper, I decided to include one more to show the option of including other hormone combinations. I felt that including all tables was redundant for this assignent. This chosen subset was enough to demonstrate standardization across the two papers' different categories of protocol input. One paper manipulates hormone concentrations while holding basal media constant at standard MS, and the other manipulates macronutrient ion concentrations while holding hormone levels constant. I built a single flat table where every row carries both the hormone columns and the macronutrient columns, filled with the actual constant value for whichever category wasn't the experimental variable in that row, rather than leaving those columns null or having a column specify a standard. A varied_input_type field records which category was manipulated for that row for interpretebility. Mean and standard error for each outcome are stored as separate numeric columns unlike the papers so the values are directly usable. I chose one flat table over a normalized multi-table schema because it is the most direct format for ML model development (one row per example, fixed feature columns), while still supporting search and aggregation well enough for this dataset's size. I moved paper-level constants that don't vary row to row, such as citation, basal medium, photoperiod, and replicate count, into a small separate source-metadata table. Most of these are identical across both papers, but a few differ slightly between them (pH 5.8 vs. 5.7, temperature 24C vs. 25C). Within each paper these conditions are constant across every treatment, so they can't explain row-to-row variation there. But still the small between-paper differences are worth flagging when comparing results across the two source tables. This metadata would also gain value if more papers were added with varied conditions.
The two papers report macronutrients in different units. The macronutrient focused paper reports ion concentrations directly in mM, while the hormone paper's fixed MS background is given in mg/L per compound. I converted the hormone paper's basal recipe to mM using the provided molecular weights and ion-dissociation tables, summing amounts across all compounds (including micronutrient salts), and validated the result against the macronutrient paper's own reported MS control row. Most of the eight almost exactly matched except for Calcium and chloride. My computed values (2.99 mM Ca2+, 5.99 mM Cl-) reflect the chemically required 1:2 stoichiometry of CaCl2·2H2O and match independently verified standard MS compositions, and differed from the paper's own reported values (3.96 mM, 2.99 mM). I kept my computed values instead of deferring to the paper's numbers, since they're chemically consistent and independently verifiable, and noted the mismatch. 

# Part 2
I would design the pipeline as a series of small, re-runnable stages, because almost every problem I hit in Part I happened at a boundary between steps (transcription, unit conversion, or a table disagreeing with the paper's own text). Raw PDFs would be stored unchanged, keyed by DOI and a content hash, and every intermediate output saved, so a bug found later can be fixed by rerunning one, avoiding reprocessing everything. Parsing would use two tools, one that understands scholarly structure (sections, captions, references), such as GROBID, and one built for reconstructing table cells and multi-level headers, such as PP-Structure. But I wouldn't committ to specific tools up front. I would benchmark a few options against a small hand-labeled set, starting with the tables i made in Part 1. An LLM would then classify extracted content as protocol input, outcome, fixed condition, metadata, or irrelevant, so that concentrations cited from other studies or used only during culture preparation aren't mistaken for tested treatments. It also would extract relevant content into teh target schema with a source reference (page and table) for every value and empty fields in place of fabrications. Tables and prose would be extracted separately so they can be checked against each other. That comparison is how I caught a results table labeling a KIN + NAA treatment as KIN + IBA. Every value would also be tagged as measured, model-predicted, or inferred, since these papers mix raw observations with ANN-GA predictions. If the goal later shifted from processing a given set of papers to building a dataset across the literature, the same pipeline could be fed by an upstream search and screening step using sources like PubMed.
Values should be normalized before validation. Compound names would be resolved through a chemical database like PubChem instead of hand-built dictionaries, and units converted to a common standard, with both original and converted values kept. This has to happen first, since some checks only work once everything is in the same units. Validation and storage are where I'd invest the most time and caution. Each row would be checked against the schema and against domain rules, including stoichiometry, plausible pH and temperature ranges, and table-versus-text agreement. My manual Ca2+/Cl- check is one example that applied, since the paper's reported values broke the 1:2 ratio CaCl2 requires, which I could only see after converting everything to mM. Rows that fail checks would go to a review queue showing the value next to its source excerpt, because a secretly "corrected" value is worse than a flagged one. For storage the flat table from Part I is still the right format for modeling, but at scale it should be generated from the database, since every new compound or outcome would otherwise add a mostly empty column. I'd use a relational store like PostgreSQL in a longer format, where a new compound is a new row. And to export tables they would be versioned flat tables so any model can be traced to the exact data it was trained on. I'd also build species, cultivar, and explant type into the schema as required fields from the start, with a step that matches different names for the same plant. Frequently papers use different terms; in this case: "G × N15", "Garnem", and "GN-15".
